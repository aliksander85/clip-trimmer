# Известные баги

## B1. Фрагментированный MP4: длительность 16 с вместо реальной, неполные миниатюры

**Статус:** закрыт, критерий готовности проверен в браузере. Найден при проверке T6, относится к T4/T5 (`workers/media.worker.ts`).

**Симптом.** Видео 186,5 с (3:06) показывается как `16.0 с`; таймлайн и миниатюры покрывают только первые ~16 секунд.

**Файл-пример.** `~/Downloads/video/Banshee  The Last Fight - Zurik 23M (1080p, h264).mp4`
(84 МБ, H.264 `avc1.640028`, 1920×1080, 23.98 fps, AAC; `ffprobe`: format duration 186.544, video 186.436).

**Структура файла** (top-level боксы): `ftyp(36)`, `moov(1411)` с `mvex`, далее пары `moof`/`mdat`
(`moof` на 1447, 2532711, 4080311, …). В `mvhd`: `timescale=1000`, `duration=0`, бокса `mehd` нет.
То есть это фрагментированный MP4 (fMP4) без длительности в заголовке.

**Причина (подтверждена по структуре файла).**
- `buildMeta` (`media.worker.ts`, ~стр. 302–307) берёт `info.duration / info.timescale` = 0 и падает на `track.samples_duration`.
- К моменту `onReady` mp4box разобрал только фрагменты из первого куска 4 МБ (`CHUNK_BYTES`), это ~16 с, поэтому `samples_duration` неполный.
- `pickWantedSamples` (~стр. 222) берёт ключевые кадры через `mp4.getTrackSamplesInfo()` сразу после `onReady`. Для fMP4 таблица сэмплов тоже неполна, поэтому миниатюры выбираются только из первых 16 с.

**Попытка исправления (откачена).** После `onReady`, если `info.isFragmented`, дочитывать файл целиком кусками по 4 МБ через `appendBuffer` без извлечения сэмплов, затем строить `meta` (длительность из `track.samples_duration`) и `pickWantedSamples`. Результат на примере выше: длительность осталась 16 с, а миниатюры перестали появляться вообще. Почему так, не выяснено. Гипотезы для проверки:
- после `onReady` mp4box при `appendBuffer` продолжает вести себя иначе (возвращаемое смещение, `flush()` на последнем куске завершает разбор и ломает последующие `seek(0)`/`start()`);
- `samples_duration` у `track` из `onReady` — снимок, не обновляется; нужно читать `mp4.getTrackById(id)` или `getInfo()` заново;
- `mp4.seek(0, true)` + `start()` после полного разбора ведёт себя иначе, чем после частичного, и `onSamples` не вызывается;
- сэмплы фрагментов могут быть выброшены из памяти, если буферы уже освобождены (`releaseUsedSamples`/`cleanBuffers`).

**Как отлаживать.** Сначала добавить dev-логи: `info.isFragmented`, `info.duration`, `track.nb_samples`, `track.samples_duration` и `getTrackSamplesInfo(track.id).length` до и после дочитывания. Альтернативы: считать длительность самим, пройдя по top-level боксам (`moof` → `traf` → `tfhd`/`trun`), либо брать её из `<video>.duration` на главном потоке (Chrome отдаёт 186 с для этого файла).

**Критерий готовности.** Для файла выше под превью `≈186.4 с`, миниатюры покрывают весь ролик, 3 файла подряд не увеличивают число bitmap. Обычные (не фрагментированные) MP4 работают как раньше. Для файла около 500 МБ проверить Memory.

**Почему не сработало наивное дочитывание** (подтверждено логами на файле-примере, mp4box 2.5.0).
- `getInfo()` возвращает копии, поэтому `track` из `onReady` не обновляется. После дочитывания в нём остаются `nb_samples` 384 и 16 с, а таблица `getTrackSamplesInfo()` уже содержит 4470 сэмплов. Свежий `getInfo()` даёт 4470 сэмплов и 186,436 с.
- У сэмплов из `moof` нет поля `alreadyRead`. Поэтому `seek(0, true)` вычисляет смещение как `NaN` и возвращает позицию разбора, а после полного дочитывания это конец файла. `readSamples` не делает ни одной итерации, `onSamples` не вызывается, миниатюр 0. До дочитывания позиция была около 4 МБ, и mp4box сам прыгал назад, поэтому раньше всё работало случайно.

**Решение.** Для fMP4 после `onReady` вызывается `indexFragments()`: он дочитывает файл до конца, пока извлечение ещё не запущено (`mdat` сразу освобождаются). Затем `info` берётся заново через `mp4.getInfo()`, а извлечение стартует со смещения сэмпла 0, а не с `seek().offset`. Обычные MP4 идут прежним путём.
- Проверено: lint, typecheck и тесты зелёные. Прогон в Node: длительность 186,436 с, извлечены все 20 нужных ключевых кадров (от 0 до 176 с), `shorts_1.mp4` без изменений.
- Проверено в браузере (Chrome, `npm run dev`):
  - файл-пример: под превью `186.4 с`, таймлайн 00:00.0 – 03:06.4, все 11 миниатюр заполнены. Тёмная миниатюра около 160 с — чёрный кадр в самом ролике (159–162 с).
  - 3 файла подряд (пример → `shorts_1.mp4` → пример): живых bitmap каждый раз 11, старые закрываются.
  - обычный `shorts_1.mp4`: `49.3 с`, 720×1280, миниатюры на месте.
  - fMP4 на 473 МБ (600 с, нарезан ffmpeg из `s1e1_1080.mp4` с `empty_moov`): метаданные за 0,6 с, все 11 миниатюр за 1,2 с.
- Memory: та же индексация mp4box в Node на fMP4 572 МБ держит 30–43 МБ, буферов `mdat` после неё не остаётся. Память воркера в браузере напрямую не замерялась: в DevTools → Memory её можно посмотреть, выбрав воркер в списке контекстов.
- Цена: fMP4 читается примерно дважды. Если на больших файлах это заметно, при индексации можно читать только `moof`.
